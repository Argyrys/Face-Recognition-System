1. Problem Statement & Objective

A VC (Vice-Chancellor) cabin entry currently has no reliable record of who entered and when. Manual register entries are slow, inaccurate and easy to forge. The objective is to build a system that identifies students and faculty at the entry point automatically.

Scope boundary (important): this prototype is software only. It detects a face, decides who it is, records it, and raises an alert. It never opens a door or controls any lock — the security guard / staff member reviews the alert and physically grants or denies access.

Objectives

  • Detect faces reliably at the entry point
  • Recognize enrolled students and faculty with a measured confidence
  • Log every entry with identity, department, ID, time and result
  • Notify staff instantly when a visitor requires attention
  • Work with or without a physical webcam (video, images, or phone camera)

2. System Architecture

The system runs entirely on one machine. A background thread pulls frames, a Flask server serves the dashboard, and everything is stored in SQLite.

4. How the Pipeline Works

Capture a frame. From the configured source (webcam, video, image folder, or phone camera over Wi-Fi).
Detect faces (YuNet). Any face found in the frame is a candidate. If no face is found, the frame is skipped silently.
Generate an embedding (SFace). The face is aligned using its 5 landmarks, then encoded into a 128-D vector that is L2-normalized.
Match against the gallery. The embedding is compared with every enrolled person using cosine similarity. Above 0.363 it is a match; below it, the system refuses to guess.
Log the entry. Name, category (Student/Faculty), department, ID, timestamp, confidence and result are written to entry_log, along with a cropped snapshot of the face.
Notify staff. A desktop toast plus a dashboard alert is raised. Staff then Acknowledge or Reject it.

Duplicate suppression

A 15-second cooldown (VC_COOLDOWN) prevents the same person (or the same unknown visitor) from being logged repeatedly while they stand in front of the camera.

What happens when a face is not recognized

The entry is logged as UNKNOWN with the raw cosine score. The system never guesses an identity — a low-confidence frame is always flagged for manual verification rather than assigned to the nearest enrolled person.

Two ways to use it

  • Live monitoring — point a webcam (or a phone camera acting as one) at the entry; the dashboard shows the feed and logs people as they pass.
  • Upload & analyze — drop in a still image and get an instant identity verdict. Useful when no camera is available.

Notification handling

Each alert can be Acknowledged (handled/allowed) or Rejected (denied). Both actions clear the notification and record the decision for audit. If nobody acts on an alert, it clears itself after 24 hours, so the notification list never grows without bound.

6. Live Camera — Phone as a Webcam

The built-in webcam on this machine was not available, so the system was built to accept a phone camera as a live source. Running an app such as IP Webcam or DroidCam on the phone exposes the camera as an MJPEG video stream over Wi-Fi, which the system consumes directly.

py app.py --source http://<phone-ip>:8080/video
Engineering note: OpenCV's FFMPEG backend buffers HTTP streams heavily — a phone camera serving ~15 fps was read at under 0.25 fps through VideoCapture. A dedicated MJPEG multipart reader (camera.MjpegStream) was written to parse the stream directly, raising throughput to ~4.3 fps at 640×480. The pipeline also auto-reconnects if the phone drops off the network.

Observed limitation: matching quality depends on how large the face is in the frame. During phone testing at 640×480 the face was only ~55–90 px wide, which pushed the cosine score down to ~0.12 and below threshold. Holding the camera closer, or using a higher stream resolution (1280×720 or above), restores accurate recognition. This is a framing issue, not a model failure — the same face scores 0.48–0.67 when properly framed.
Design strength: the system errs on the side of caution. A low-confidence face is logged as UNKNOWN and flagged for a human rather than being force-matched to the closest person. In the evaluation above, zero false acceptances occurred.

8. Security, Privacy & Ethical Considerations

Consent-first enrollment

Enrollment requires an explicit consent checkbox. No face is enrolled without it. Face embeddings are stored as binary blobs, not photographs.

Data locality

  • All data lives locally: database/vc_entry.db plus snapshot images in static/snapshots/
  • Nothing is uploaded to any cloud service or third party
  • Full erasure = delete the database folder and snapshots folder
  • Snapshots are capped (240 most recent) and pruned automatically

Human-in-the-loop by design

The software produces a recommendation, never an action. Every alert requires a human Acknowledge/Reject, and no physical access control is driven by the system.

Limitations and bias

  • Accuracy depends on lighting, distance and face size in frame
  • Trained primarily on adult faces — performance on very young or elderly subjects may differ
  • The enrolled gallery determines who can ever be recognized; unknown faces are never guessed

What this prototype does NOT do

No door control, no lock control, no automated entry grant. The prototype stops at identification, logging and notification.
